# 星座速配 · AI 分析提示词设计

| 项目 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 日期 | 2026-11-19 |
| 配套实现 | `server/prompt.js`（提示词正文）、`server/server.js`（SSE 代理） |
| 交互定位 | 结果页**默认展示算法结果**，AI 是用户主动点击后的「深度解读」，不影响主流程 |

---

## 1. 为什么要 AI，但不让 AI 打分说了算

算法负责**确定性**：同一组输入永远是同一个分数，可复现、可解释、不花钱。

AI 负责**表达力**：把「三分相 +4」这种机器语言，翻译成「你们吵完架谁先低头」这种有画面的判断。

所以在设计上做了三个约束：

| 约束 | 做法 | 目的 |
| --- | --- | --- |
| 分数不飘 | 把算法分作为**基准锚点**传给模型，限定 ±12 浮动 | 避免「AI 说 30 分、页面写 88 分」的自相矛盾 |
| 结果可解释 | 要求分数与文字结论**方向一致** | 避免 85 分却通篇写不合适 |
| 主流程不被阻塞 | AI 是可选增强，失败静默降级 | 接口挂了页面照样能用 |

页面上的关系是：**算法分是主视图**（环形指数 + 三张卡），**AI 分是补充视角**，并标注与算法的差值。

---

## 2. 输入契约

前端只传**索引和数值**，不传任何自由文本，星座元信息由服务端维护：

```jsonc
{
  "a": { "sign": 0, "age": 26, "gender": "male" },   // sign: 0-11
  "b": { "sign": 4, "age": 24, "gender": "female" }, // age: 18-60 或 null
  "base": { "couple": 88, "spouse": 85, "friend": 91, "overall": 88 },
  "relation": ""                                      // 可选：用户关心的关系
}
```

> 这样做的原因：如果把用户输入直接拼进 prompt，任何可输入的字段都是注入面。服务端用白名单把 `sign` 映射成星座事实卡，`age` 校验为整数，`gender` 只接受枚举值，拼装出来的 prompt 结构就是不可控改写的。

## 3. 提示词结构

整体 4 段，顺序是有讲究的：

```
角色设定  →  信息边界  →  写作要求  →  打分规则  →  输出格式
```

**为什么把「信息边界」放在很前面**：不做限制的话，模型会主动补出「你的上升在天蝎」这类信息。用户并没有输入出生时间，这类内容一旦出现，产品的可信度直接崩。所以明确写死：只能用太阳星座 + 元素 + 模式 + 年龄 + 性别。

**为什么要求「具体优于形容」**：星座文案最容易滑向形容词堆砌。给出「怎么吵架、周末怎么过、钱怎么花」这种可观察的行为样例，比写「要写得具体一点」有效得多。

**为什么单列「允许有锋芒」**：全是好话就没有分享欲，但放开批评又容易变成劝分。所以给了一个边界：可以指出摩擦，但**落点必须是可以操作的相处建议，或者可以被接受的差异**，并且禁止绝对化断言。

## 4. 完整提示词

以下与 `server/prompt.js` 中的 `SYSTEM_PROMPT` 保持一致，改提示词只改那一个文件。

### 4.1 System Prompt

```text
你是「星座速配」小程序里的资深星座内容作者，擅长用太阳星座写轻松、具体、有画面感的关系解读。读者是普通年轻人，正在好奇自己和某个人到底合不合。你要写得像一个很懂星座、又不装神弄鬼的朋友在跟他聊天。

# 你只能使用这些信息
太阳星座（含元素、模式、极性）、年龄、性别的可选信息、以及系统给出的算法基准分。
不要编造上升星座、月亮星座、宫位、行星相位、星盘、血型、星座运势日期等任何不存在的信息。也不要引用「某星座今日运势」这类内容。

# 写作要求
1. 具体优于形容。每个判断都要落到可观察的行为：怎么吵架、怎么表达喜欢、周末怎么过、钱怎么花、冷战多久会先低头。不要通篇堆「温柔」「有魅力」这种空词。
2. 允许有锋芒。可以指出真实的摩擦点，但落点必须是可操作的相处建议，或可以被接受的差异。不做绝对化断言：不写「一定会分手」「注定不幸」「绝对不合适」。
3. 用「TA」指代 A，用「你」指代 B。可以提到性别与年龄，但不得据此做优劣判断，不得使用「男人就该…」「女人总是…」这类表述，不物化任何一方。
4. 娱乐向。不宣称科学，不给医疗、法律、投资建议，不评价谁配不上谁。
5. 用简体中文口语写作。输出纯文本：不要 Markdown（不用 #、##、**、-、>），不要 emoji，不要「首先 / 其次 / 综上」这类作文腔，不要加任何开场白或结束语。

# 打分规则
1. 恋人、夫妻、朋友各给一个 0–100 的整数。
2. 系统会给出一组算法基准分。你的分数应当在基准分 ±12 以内；只有你有明确理由时才可突破，但最多 ±18。
3. 三个分数不能全部相同，必须有区分度，而且谁高谁低必须和后面的分析文字一致。
4. 65–85 是常态区间，不要给所有组合都打高分，也不要为了戏剧性刻意打低分。
5. 三个维度的判断标准不同：
   - 恋人：看吸引力、张力、心动感，差异有时反而是火花；
   - 夫妻：看长期共处的稳定性、生活节奏、冲突修复能力，激情不是主要因素；
   - 朋友：最宽容，看相处是否轻松、有没有共同语言。

# 输出格式（必须严格遵守）
按下面 6 个分段顺序输出。每个标记必须独占一行，内容紧跟在标记的下一行。
关系分段的第一行只写一个数字（分数），第二行起才是分析文字。

<<<A>>>
（A 的性格，2–3 句，60–110 字）
<<<B>>>
（B 的性格，2–3 句，60–110 字）
<<<COUPLE>>>
（只写分数，纯数字）
（恋人维度分析，2–3 句，60–110 字）
<<<SPOUSE>>>
（只写分数，纯数字）
（夫妻维度分析，2–3 句，60–110 字）
<<<FRIEND>>>
（只写分数，纯数字）
（朋友维度分析，2–3 句，60–110 字）
<<<SUMMARY>>>
（一句话总结，40 字以内，要有记忆点，适合被截图转发）

除这 6 个标记外，不要输出任何其他标题、编号或说明。全文控制在 600 字以内。
```

### 4.2 User Prompt 模板

```
请为下面两个人写一份星座配对解读。

【A】白羊座 · 火象 · 基本宫 · 26 岁 · 男
核心特质：直接、冲动、先做后想，讨厌拖泥带水
【B】狮子座 · 火象 · 固定宫 · 24 岁 · 女
核心特质：自信、大方、需要被认可，有主角意识

【元素关系】同元素，节奏一致但容易一起上头
【年龄差】相差 2 岁
【用户关注的关系】未指定，三个维度都需要完整评价
【算法基准分】恋人 88 · 夫妻 85 · 朋友 91 · 综合 88
（基准分只用于锚定，你需要在此基础上给出自己的判断，并说明理由）

请严格按约定的 6 个分段格式输出。
```

### 4.3 生成参数

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `temperature` | 0.85 | 文案需要文采和变化，太低会写得像模板 |
| `top_p` | 0.9 | 与温度配合，收敛一下尾部随机性 |
| `max_tokens` | 1200 | 目标 600 字中文，留余量防止截断 |
| `presence_penalty` | 0.3 | 减少反复使用同几个词 |
| `frequency_penalty` | 0.2 | 同上，轻微即可 |

## 5. 输出协议：为什么用分段标记

### 5.1 为什么不直接让 AI 返回 JSON

JSON 在流式场景下体验很差：`{"couple":{"score":` 这种半截结构没法渲染，用户会盯着一个空白框等十几秒。

### 5.2 分段标记的方案

```
<<<COUPLE>>>
85
你们之间最有意思的地方是...
```

- 标记**独占一行**，前端按行切分，天然解决「标记被拆在两个 chunk 里」的问题；
- 每段内容一到达就能立刻渲染到对应位置，首字出现时间约等于首 token 时间；
- 标记用 `<<<>>>` 而不是 `###`：前者不是 Markdown 语法，模型不会顺手把它渲染成标题。

### 5.3 解析规则（前端实现要点）

| 情况 | 处理 |
| --- | --- |
| 按 `\n` 切行，最后不完整的行留在缓冲区 | 避免半个标记被误判 |
| 行内出现 `<<<KEY>>>` | 也支持，按标记切分同一行内容 |
| 关系段的第一行 | 用 `/^\s*(\d{1,3})/` 提取分数，剩余部分作为分析正文 |
| 第一行还没换行结束 | 先不显示分数，等换行后再解析（防止 8 / 5 分两次到达） |
| 未知标记 | 忽略标记本身，内容并入当前段 |
| 一个标记都没解析到 | 全部文本降级显示在「总评」区，不报错 |
| 流中断 | 已收到的内容保留，提示「分析中断，可重试」 |

## 6. SSE 事件协议

前端用 `fetch` + `ReadableStream` 而不是 `EventSource`，因为需要 POST 传参。

**请求**：`POST /api/ai/analyze`，`Content-Type: application/json`

**响应**：`Content-Type: text/event-stream`

| event | data | 说明 |
| --- | --- | --- |
| `meta` | `{"model":"...","ts":1732000000000}` | 首帧，告知使用的模型 |
| `delta` | `{"t":"文本片段"}` | 增量文本，前端直接拼接 |
| `done` | `{"chars":612,"ms":8200}` | 正常结束 |
| `error` | `{"message":"..."}` | 出错，前端展示降级提示 |

```
event: meta
data: {"model":"deepseek-v3"}

event: delta
data: {"t":"<<<A>>>\n白羊座的人"}

event: done
data: {"chars":612,"ms":8200}
```

服务端还会定期发送 `: ping` 注释帧，防止中间层（Nginx / CDN）因空闲断开连接。

## 7. 安全与降级

| 风险 | 措施 |
| --- | --- |
| API Key 泄露 | Key 只存在服务端环境变量，前端永远拿不到；这是必须走后端代理的根本原因 |
| 提示词注入 | 前端不传自由文本，服务端用 `sign` 索引映射事实卡，数值字段强校验 |
| 刷接口烧钱 | 按 IP 限流（10 次 / 分钟），单请求超时 45s，`max_tokens` 封顶 |
| 上游挂了 | 返回 `error` 事件，前端展示「AI 暂时不可用」，算法结果不受影响 |
| 内容越界 | prompt 内禁止医疗 / 法律 / 投资建议、绝对化预言、性别优劣评价 |
| 成本 | 单次约 600 字输出，按国产模型价格约 ¥0.001–0.003 / 次 |

**降级三层**：

1. 有服务 + 有 Key → 真实 AI 流式；
2. 有服务 + 无 Key → `health` 返回 `configured:false`，前端仍走本地模拟并明确标注；
3. 直接双击 HTML（`file://`）→ 请求失败，自动切本地模拟，保证原型可演示。

**补充：有 Key 但上游拒绝**（401 / 402 / 403 / 429 / 404）时，前端在「一个字都没吐出来」的情况下自动降级演示，并在状态栏写明真实原因，例如：

> 真实 AI 不可用（该 API Key 所属账号无对话权限：Account is not permitted to use chat services（account_chat_banned））· 当前为演示内容

同一次会话内会记住这个失败（`AI.dead`），后续点击直接走演示，不再白等一次往返；刷新页面即可重试真实接口。

服务端会把最近一次失败记录在 `lastError` 里，`GET /api/ai/health` 可以直接看到 `status` / `hint` / `upstream` 三个字段，便于排查。

## 8. 本地模拟的设计

原型需要「双击就能看效果」，所以内置了一个本地生成器：

- 用真实选择的星座、年龄、算法分拼出结构相同的文本，不是死文案；
- 按 12–24ms 随机间隔逐段吐出，模拟真实的流式节奏；
- UI 上明确标注「演示模式」，不伪装成真实 AI。

它的作用是**验证交互与排版**，正式环境必须走服务端。

## 9. 启动方式

推荐把配置写进 `server/.env.local`（已被 `.gitignore` 忽略，不会入库）：

```ini
AI_BASE_URL=https://api.qnaigc.com/v1
AI_MODEL=deepseek/deepseek-v4.1-flash-1017
AI_API_KEY=sk-xxxxxxxx
PORT=8787
```

```bash
# 启动（零依赖，不需要 npm install）
node server/server.js
# 或
npm start

# 打开
open http://localhost:8787
```

服务端会零依赖解析 `.env.local`；**命令行已有的环境变量优先**，所以临时换 Key 直接覆盖即可：

```bash
AI_MODEL=deepseek-v3 node server/server.js
```

未配置 Key 时服务仍可启动，`/api/ai/health` 会返回 `configured:false`。

### 9.1 上游对不通报错对照

| HTTP | 含义 | 处理 |
| --- | --- | --- |
| 401 | Key 无效或已过期 | 换 Key |
| 402 | 账户余额不足 | 充值 |
| 403 `account_chat_banned` | 账号无对话权限（未开通 / 未实名 / 被风控） | 到控制台开通「AI 大模型推理」服务或联系客服 |
| 404 | 模型名或接入点错误 | 核对 `AI_MODEL` / `AI_BASE_URL` |
| 429 | 限流 | 降频或升级配额 |

> 注意：请求示例给的是 `stream: false`，本项目**必须用 `stream: true`**，否则拿不到逐字效果。国产 OpenAI 兼容网关一般都支持，若某模型不支持会返回 400，此时把 `server.js` 里的 `stream` 改回 `false` 并整段返回也能跑，只是失去流式体验。

## 10. 后续可迭代方向

1. **关系场景化**：用户可选「想看恋爱 / 婚姻 / 友情」，prompt 里调整侧重，输出篇幅集中在一个维度。
2. **多候选**：同一组输入生成 2 个不同风格的解读（治愈系 / 毒舌系），让用户切换。
3. **缓存**：`sign` 组合 + 年龄分段做 key，命中缓存直接回放，省 token 也更快。
4. **结构化校验**：服务端在流结束后校验分数是否落在 ±18 区间，越界时用算法分替换并在前端标注。
5. **多模型对比**：同一 prompt 并行调两个模型，让用户选「更喜欢哪个版本」。
